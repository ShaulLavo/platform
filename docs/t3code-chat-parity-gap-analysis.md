# T3Code Chat Parity — Verified Gap Analysis and Roadmap

> Synthesized from twelve independently verified dimension audits (2026-08-09). Every claim below carries a
> file-and-line verification from the audits; severities are the **post-verification** ones, not the raw
> reporter estimates. Supersedes the phase-status blocks in `docs/t3code-parity-implementation-plan.md`
> (see [Corrections](#corrections-to-the-existing-plan-doc)).

## Bottom line

**We are at ~40% of full T3Code chat parity, and ~55% of the parity we actually intend to build.** The architecture
spine is real and in several places better than the reference: event-sourced core with per-aggregate stream versions,
persisted command receipts (vs the reference's bare `{sequence}`), a single append+project+receipt transaction,
`actorKind` on every event envelope, structured `GitFileDiff[]` diff results, and a normalized client projection store
with double sequence guards. What is missing is almost entirely **above** the spine.

The remaining work has three distinct shapes, and only the first is urgent:

1. **Dead ends — the agent can block and the user cannot unblock it.** There is no approval UI, no user-input answer
   UI, and no runtime-mode picker. Because `DEFAULT_RUNTIME_MODE = 'full-access'` maps to Codex `danger-full-access`
   and Claude `bypassPermissions`, every turn today runs unsupervised — and the moment a user types `/plan`,
   Claude's `ExitPlanMode` and Codex's `tool/requestUserInput` park on a promise nothing can resolve. Separately,
   **no checkpoint is ever captured**, so every checkpoint-shaped thing we built (revert command, diff queries, ref
   naming, changed-files tree, revert pruning) is dead code, and every `git-diff:` document opens an empty pane.
2. **Silent data loss and permanent lies.** A page reload drops every proposed plan and every per-turn changed-files
   summary because the thread-detail snapshot cannot carry them. `pendingApprovalCount` / `pendingUserInputCount` are
   written once as `0` and never recomputed. `hasActionableProposedPlan` latches to `true` forever. Historical
   work-log activity is filtered out of the timeline entirely — scroll back and there are no tool calls at all.
3. **Breadth we chose not to build yet.** Inbox lifecycle (settle/snooze/pin/unread), thread search, worktrees,
   provider driver SPI and multi-account, a settings system, terminal-selection capture, pagination.

Realistic total for true parity: **~300–360 engineer-days** (~14–18 engineer-months solo; ~5–6 months for three).
The first four milestones — roughly **90 days** — buy the whole of (1) and (2): the agent never dead-ends, nothing is
silently lost on reload, and checkpoints work end to end. Everything after that is breadth, and can be sequenced by
product appetite. **24 verified gaps are deliberate non-parity** and are excluded from that number
([why](#deliberate-non-parity)).

- M0's rows are mutually independent; so are M1's three main threads (invariants / receipt scoping / turn settling).
- **M2 and M3 can run concurrently** after M1 — different files, different people. Both are blockers.
- The M3 **diff viewer** (XL) is independent of checkpoint capture and also unblocks the _existing_ git panel's dead
  `git-diff:v2:` documents, so it can start immediately and has standalone value.
- M5 (timeline) and M6 (composer) share no files and can overlap once M4 lands.
- M8's provider work splits cleanly: the resume-cursor + `sessionModelSwitch` fixes (high, small) are independent of
  the driver SPI (XL) and should ship first, well ahead of the rest of the milestone.
- The settings system (M8) is a hard prerequisite for user keybindings and model hide/reorder, but nothing else.

**Serialize strictly:** ledger → any new column. Event bus → checkpoint and deletion reactors. Proposed-plan table →
snapshot completeness → plan follow-up. Pending-approval projection → settle guards. Background-liveness signal →
session reaper (a reaper without it kills long-running subagent work).

## Convention notes for implementers

Per `CLAUDE.md`, applied to every target path above:

- **Files are kebab-case; group by feature then kind.** New server modules go in the owning feature dir
  (`apps/server/src/orchestration/command-invariants.ts`, `apps/server/src/orchestration/checkpoint-reactor.ts`,
  `apps/server/src/git/checkpoint-store.ts`), not a shared `lib/`.
- **`utils/` is the home for pure, stateless, non-React code.** `features/chat/lib/` is the existing de-facto home and
  now holds a lot of pure logic (`chat-work-log.ts`, `chat-input-logic.ts`, `chat-timeline-items.ts`). New pure modules
  should go in `utils/`; the feature should be normalized in one pass rather than growing two homes further.
- **No barrels.** Import exact files through `@/`.
- **One component per file, one hook per file.** The M2 panels are three components, not one.
- **No prop drilling.** Approval/user-input/runtime-mode actions cross more than two component boundaries — expose them
  as narrow provider actions (`respondToApproval`, `setRuntimeMode`) from a chat feature provider, not as props threaded
  through `chat-view` → `chat-input` → `chat-input-actions`.
- **Never-nester.** Decider invariants, the pending-approval fold and the work-log status classifier are all guard-clause
  shaped; keep nesting ≤ 3 and never use a nested ternary.
- **Theme tokens only.** Approval panels use `warning`, failures `destructive`, plan-ready `info`, tool success
  `success`. Floating panels (approval, user-input, command menu) use `surface-vibrancy`; in-pane chrome uses
  `backdrop-material`. No raw palette colors and no hand-rolled dark variants.
- **`tabular-nums` on every updating number:** approval counters (`1/N`), plan step counters (`3/7`), turn durations,
  diff stats, context-window percentages.
- **Errors via `createError`/`createStructuredError`, never `new Error`.** The checkpoint failure catalog (M3) is
  exactly the case `defineErrorCatalog` exists for — five reasons with `code`/`why`/`fix`, replacing the client's
  current `message.includes('fromturncount')` retry.
- **Logs are wide events.** Enrich the one event per operation (add `resumeCursorPresent`, `restartReason`,
  `checkpointTurnCount`, `pendingApprovalCount`) rather than emitting extra narrow lines.
- **Tests are Vitest against the real in-process server** — `apps/web/test/fixtures.ts`, real `treaty` client,
  `MockProviderAdapter` (a production adapter, not a stub) for the approval/user-input/checkpoint flows, a real
  `git init` temp repo for checkpoint capture and revert. Run app tests with `bun --bun vitest`. Do not `vi.mock` our
  own modules. Note the known `--project browser` hang: prefer node/dom projects, or drive the running dev server at
  `:5173` via Playwright.
- **Greenfield.** When these fixes invalidate persisted state (localStorage drafts, the SQLite file, checkpoint refs),
  delete it or tell the user what to delete. Do not write healing code.
